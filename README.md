# SmartRail-Seat-Engine：高铁选座决策引擎（V1.0 启发式 → V2.0 运筹学 → V3.0 强化学习）

## 项目简介

**SmartRail-Seat-Engine** 是一个从零实现的**铁路客运选座决策引擎**，用**分层罚函数 + 状态机**把"选座"这件看起来简单的事情，拆解成一套可解释、可测试、可降级的工程系统。

选座的本质是一个**带硬约束的组合优化问题**：座位是有限的二维资源，乘客之间又存在强弱不一的同行关系（带娃家庭、轮椅旅客与陪护、孕妇与同伴、静音车厢偏好……）。真正的难点不在"找到一个空位"，而在于：

- **底线不能破**：带娃家庭被拆散、轮椅旅客被分到非无障碍座位这类事故，任何情况下都不允许发生；
- **优先级要分明**：同样是"不理想"，把儿童和父母分开与"成人没坐到靠窗"，严重程度差了三个数量级；
- **结果要能解释**：调度员和旅客都需要知道"为什么这么排"；
- **高负载要能活**：春运峰值下必须自动降级，宁可给次优解也不能超时或崩溃。

项目分三代演进，**三代共用同一套代价函数与评估口径**，因此可以直接并排对比：

| 版本 | 技术路线 | 求解方式 | 定位 |
| :--- | :--- | :--- | :--- |
| **V1.0** | 规则 + 分层罚函数 | 优先级单元 + 分支限界（零第三方依赖） | ✅ **生产主线（最终交付）** |
| **V2.0** | 运筹学（OR-Tools CP-SAT） | 布尔约束建模 + 目标函数线性化 | ✅ 精确求解路线（**代码完成，本机缺 ortools 未运行验证**） |
| **V3.0** | 强化学习（GNN + PPO + 行为克隆） | 二分图编码 + 序列决策 | 🔬 探索路线（**代码保留，未替代 V1+V2**） |

> **一句话结论**：V1 是生产主线，V2 是精确求解的补强，**V3 是探索且未被采用**。
> V3 的训练努力与三条负面结论都完整写进本文件（见"踩坑记录"8/9/10 与
> "V3.0 训练复盘"），代码一行未删 —— 它们比"又一个效果一般的模型"更有长期价值。

## 核心成绩

### V1.0 —— 底线守卫与可解释性

- **Tier 0 违规 0 条**：在 300 单 / 788 位乘客的仿真中，跨车厢拆散硬绑定、轮椅无无障碍座位、孕妇无同伴三类事故**均为 0**。这不是"调参调出来的"，而是候选池结构性排除 + 巨额罚分 + 断言守护三层保障。
- **带娃家庭不被拆分**：`family_with_child` 场景稳定输出 `01车[A1@01A A2@01C C1@01B]` —— 儿童被夹在双亲之间（相邻三座），代价 -130（负值代表奖励，约束满足良好）。
- **可解释性**：每一次分配都能输出"逐条代价明细"，例如 `T5_CHILD_ADJACENT +50（儿童紧邻家长）`、`T4_NOT_SAME_ROW −30（未同排）`，而不是只给一个分数。
- **降级容灾**：峰值场景（85% 预占座）下模式分布自动变为 `smart 46 / degraded 11`，降级时仍保持 **Tier 0 = 0**。

| 场景 | 订单数 | 就座乘客 | 模式分布 | Tier 0 | P50 | P95 | P99 |
| :--- | ---: | ---: | :--- | ---: | ---: | ---: | ---: |
| 平峰（空车起售） | 300 | 788 | free 230 / smart 70 | **0** | 3.02 ms | 9.83 ms | 23.73 ms |
| 峰值（85% 预占） | 47 | 119 | smart 39 / degraded 8 | **0** | 1.03 ms | 4.76 ms | 6.97 ms |

> **未达标项（如实说明）**：设计目标是 **P99 < 15 ms**，实测平峰 P99 = 23.73 ms，**仍未达标**（峰值场景 6.97 ms 已达标）。原因是团体长尾订单（6 人以上）触发分支限界搜索，单笔耗时可达 24 ms。缓解手段是自适应预算 + 降级贪心（已生效，故 Tier 0 仍为 0），根治手段是 V2.0 的 CP-SAT 与批量求解。
>
> 这组数字是在**修正编组容量之后**重测的（见坑点 11）：旧编组把商务座夸大成 51 座、总容量 1156 座，容量虚高会让压力测试偏乐观。

### V2.0 —— 运筹学建模

- **CP-SAT 完整建模**：Tier 0/1 写成布尔硬约束，软约束写成目标函数线性化项，详见下文"CP-SAT 建模要点"。
- **零依赖后端可用**：`v2_exact` 在没有任何第三方库的环境下与 V1 给出**逐座位完全一致**的分配。
- **算法件独立验证**：自研匈牙利算法通过 **40+ 组随机矩阵**（含 big-M 稀疏、矩形、负值）与暴力枚举交叉验证，全部一致。
- **诚实边界**：本机 **无法安装 `ortools`**（详见"环境限制说明"），CP-SAT **未经过真实运行验证**，仓库与验收页都把它显式标记为不可用，并以 `BackendUnavailable` 报错而非静默换引擎。

| 策略 | 订单流 | 就座率 | 候补 | 亲和度 | Tier 0 | 孤立照护 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| **V1 启发式** | 30 / 60 / 120 步 | **1.000 / 1.000 / 1.000** | **0** | **3675 / 7660 / 15035** | 0 | **0** |

**为什么最终不用 V3**（每一条都有上面的数字支撑）：

1. **质量没赢，而且差距很大**：行为克隆的就座率**从未追平 V1**（最好 93% vs 100%），
   亲和度低 **2 个数量级**（−17.9 万 vs +3675），孤立照护最多 68 例 vs V1 的 0 例；
2. **随订单流变长持续退化**：93% → 88% → 74%。这说明学到的策略**不具备 V1 那种
   "长期占座管理"能力** —— V1 每单都在全局视角下搜索，而策略只看当前订单的局部特征，
   早期"图省事"的落座会不断蚕食后续订单的可行性；
3. **速度慢 5 倍**：V3 单步要跑 GNN 前向（P50 12.2 ms），V1 分支限界只要 2.4 ms；
4. **依赖更重**：V3 需要 PyTorch + NumPy，而 V1 零第三方依赖；
5. **可审计性更差**：V1 的每条决策都能追到具体代价条目，学习型策略只能给出打分。

> **口径更正说明**：本文件早期版本写过"行为克隆把就座率提升到 100%"。
> 那是**训练期评估口径**（30 单、老师解在候选池内投影、且评估与训练同分布）的结果，
> 与上面这套**统一验收口径**不一致。按统一口径复测后，该结论不成立，已更正。
> 保留这条说明是为了避免"文档里的漂亮数字"再次误导后续判断。

**留下什么**：完整的行为克隆流水线（可复用于"从历史投诉学偏好权重"）、
二分图 GNN 编码器、自研 PPO、以及 3 条写进"踩坑记录"的负面结论
（见坑点 8/9/10）。这些比"又一个效果一般的模型"更有长期价值。

**展望**：V3 真正值得投入的方向**不是**"让网络直接输出选座动作"（这条已被上面的
数字否掉：局部决策打不过整单搜索），而是**从历史投诉与换座记录里学习偏好权重**，
替代当前人工标定的 Tier 权重 —— 那才是学习型方法相对运筹学的比较优势所在
（规则说不清、结果好评价）。

## 🧮 分层代价函数（Tier 0-5）

整套引擎的核心是这个**分层罚函数**。设计原则：**层级之间量级差至少一个数量级**，保证任何情况下高优先级的约束都不会被低层级的奖励淹没。

| 层级 | 权重 | 触发条件 | 语义 |
| :--- | ---: | :--- | :--- |
| **Tier 0** | −100,000 | 硬绑定被跨车厢拆散 / 轮椅旅客无无障碍座位 / 孕妇无同伴 | **绝对底线，不可违反** |
| **Tier 1** | −10,000 | 易受伤害旅客或照护单元被跨车厢拆开 / 硬冲突群体被孤立 | 严重事故 |
| | −3,500 | `T1_ISOLATED_CARE_MEMBER`：需照护者身边没有支持人 | 安全底线 |
| | −60 | `T1_CARE_BOND_SAME_CARRIAGE`：同车厢但未相邻 | 轻微不理想 |
| **Tier 2** | −3,000 | 成人同行人跨车厢 | 体验受损 |
| **Tier 3** | −2,500 × 排斥度 | 带娃家庭占用静音车厢 | 冲突 |
| | −800 / 人 | `T3_QUIET_GROUP_EXTRA`：团体超员占用静音车厢 | 资源误用 |
| | −5,000 | 被投诉屏蔽的旅客仍被排入静音车厢 | 信用机制 |
| **Tier 4** | −10 / −30 | 被过道分隔 / 未同排 | 舒适度 |
| **Tier 5** | +50 / +40 / +30 / +20 | 静音车厢独行成人 / 无障碍匹配 / 同伴同座 / 设施匹配 | 正向奖励（**每人封顶 60**） |

### 两个关键设计决策

**1. Tier 0 用"结构性排除"而不是"巨额罚分"。** 轮椅旅客的候选池在建模阶段就只保留无障碍座位，硬绑定双方只保留共同车厢的候选。这样 Tier 0 从"罚分很重"升级为"**不可行**"，语义更强，也不会因为其他项累加而被意外抵消。

**2. 奖励必须有硬上限。** 早期版本没有 `max_reward_per_passenger`，导致 Tier 3 的静音车厢奖励按人头累加，**反向利好**"家庭坐静音车厢"这个错误行为。现在每人奖励封顶 60 分，且设有 `min_floor_reward = 10.0` 的碎片化奖励地板。

## 🚄 12306 风格购票流程（用户模式 / 开发者模式）

`/ticket` 与 `/dev` 两个页面严格对齐 12306 的真实交互，与前面的"座位图工具页"
（`/`、`/booking`、`/ticket-first`、`/acceptance`）**并存但职责分开**：
后者是调试与压测工具，前者是面向旅客的购票流程。

### 用户模式（`/ticket`）

| 环节 | 实现 |
| :--- | :--- |
| 车次列表 | 北京南 → 上海虹桥，G25 / G35 / G531，各席别余票与"有票 / N张 / 无" |
| 预订 | 点"预订"进入确认订单页，可选二等座 / 一等座 / 商务座 |
| 选择乘车人 | 列表为空时引导添加；已有乘车人时也能**继续添加** |
| 添加乘车人 | 下拉选择**人群类型**（16 种，分 5 组） |
| 提交限制 | **必须先添加乘车人**才能提交 |
| 选座服务 | **只显示一排 A / B / C / D / F** 供选偏好 |
| 静音车厢 | 勾选项，标注 03 / 11 车 |
| 自动分票 | **仅当多人订单且余票无法满足选座要求时**才介入，并明示原因 |

**用户端看不到整列车的座位分布图** —— 这是需求明确要求的，也是本模块与
`/booking` 的根本区别。`/ticket` 页面的 HTML 里**没有任何座位图容器**，
也不调用任何 `/api/dev/*` 接口（由 `tools/verify_ticketing.py` 断言守护）。

### 开发者模式（`/dev`）

| 功能 | 实现 |
| :--- | :--- |
| 预制数据 | **各类人群各一位**，共 16 位默认购票人 |
| 模拟余票 | 滑杆调整某席别余票，**实时影响用户模式** |
| 全局座位图 | 16 节编组完整座位图，区分"用户已售 / 手动锁定 / 预设占用" |
| 静音车厢标记 | 03 车与 11 车，座位图上有紫色描边 |
| 分票映射 | 用户下单的座位在座位图上按订单着色，并标注乘客姓名 |
| 重置系统 | 一键清空订单与占用，乘车人回到预制状态 |
| 快速压测 | 空车 / 三成 / 六成 / 八成五 / 满座 |

**余票只有一个数据源。** 开发者调整余票的实现方式是"占用/释放座位"，
而不是维护一个独立的 `remaining` 计数器 —— 后者会与实际座位图谱逐渐漂移，
最终产生"显示有票但下单失败"这种最招人骂的状态。所以余票一律由
`总座位 − 已占用` 实时算出（见 `smartrail/ticketing/devstore.py`）。

### 接口

| 接口 | 用途 |
| :--- | :--- |

### ⚡ 性能特征说明

本项目的瓶颈**不在算力，而在团体长尾**：

1. **单笔订单的复杂度随人数指数上升**。2-4 人订单走精确搜索，耗时 < 10 ms；6 人以上触发分支限界剪枝，P99 被拉到 49 ms。
2. **CPU 单核性能是决定因素**。引擎是纯 Python 实现，无矩阵运算；`FastScorer` 用**惰性向量化**（首次访问某乘客时才构建整行亲和度）把平均耗时压到 8.6 ms。
3. **GPU 对本项目几乎无用**。唯一的 GPU 用途是 V3.0 的 GNN 前向，而单次推理只有几毫秒、批量极小，实测**在 CPU 上训练反而更快**（避免频繁的设备搬运），因此 V3 训练统一使用 CPU。

## 🧩 人员构成与出票规则（OrderEditor）

`/booking` 页面下半部分是**按人员构成组单**的编辑器。核心口径只有一句：

> **基础分组管总人数；儿童细分、残疾、孕妇是独立维度，只做标签与出票规则。**

### 基础分组（总人数的唯一来源）

| 分组 | 说明 |
| :--- | :--- |
| 成人 | 满 18 周岁及以上 |
| 青少年 | **满 14 周岁**但未满 18 周岁 |
| 儿童 | 满 4 周岁但**未满 14 周岁** |
| 幼儿 | 满 1 周岁但未满 4 周岁 |
| 婴儿 | 未满 1 周岁 |

```text
总人数 = 成人 + 青少年 + 儿童 + 幼儿 + 婴儿
```

> 14 岁整属于**青少年**：儿童是"未满 14 周岁"，青少年是"满 14 周岁"，
> 两者在 14 岁整这一点上不重叠。代码里由 `minors_under_14 = 婴儿+幼儿+儿童`
> 体现（不含青少年）。

### 三个不计入总人数的维度

| 维度 | 结构 | 是否计入总人数 |
| :--- | :--- | :--- |
| **儿童细分** | 安静 / 吵闹 | 否（只是行为标签） |
| **残疾** | 程度（轻度/中度/重度/极重度）× 年龄段（5 档） | 否 |
| **孕妇** | 孕期（1-3/4-6/7-9/10 个月·37 周+）× 年龄段 | 否 |

残疾与孕妇**和基础分组平级**，不挂在成人下面 —— 因为残疾人、孕妇也可能是
青少年、儿童、幼儿、婴儿。**陪同人本身已计入基础分组成人**，不额外加总人数。

### 出票规则（不满足则不予出票）

| 规则 | 判定 |
| :--- | :--- |
| 婴儿 / 幼儿 / 儿童单独购票 | **拒票**，必须至少 1 名成人陪同 |
| 青少年（14-18 周岁）单独购票 | **不拒票**，可独立购票 |
| 陪同人资格 | 必须是成人（18+）；**重度/极重度残疾人不能充当陪同人** |
| 重度 / 极重度残疾 | **必须预约重点旅客服务**，且每位至少 1 名成人陪同 |
| 孕妇 1-6 个月 | 可独立购票，不强制 |
| 孕妇 7-9 个月 | **平台可配置**是否要求重点旅客/陪同 |
| 孕妇 10 个月 / 37 周+ | **必须预约重点旅客服务**，且至少 1 名成人陪同 |

可用健康成人的算法：

```text
可用健康成人 = 基础分组成人 − 成人中重度残疾数 − 成人中极重度残疾数
最终出票条件：可用健康成人 >= 所需成人陪同
```

### 模块划分（每个分组独立渲染、独立 testId、独立纯函数校验）

```text
OrderEditor
├─ OrderSwitcher      订单1…订单n 切换（数据隔离）
├─ BaseGroup          基础分组（总人数唯一来源）
├─ ChildSubGroup      儿童细分（安静/吵闹）
├─ DisabilityGroup    残疾（程度 × 年龄段）
├─ PregnantGroup      孕妇（孕期 × 年龄段）
├─ CompanionCounter   陪同人数（可选登记）
├─ ServiceGroup       重点旅客 / 轮椅 / 担架 / 导盲犬 / 无障碍车厢
├─ OrderSummary       总人数、可用健康成人、所需陪同、校验提示
└─ OrderActions       提交、新建、复制、清空
```

校验是**纯函数**（`smartrail/composition.py` 的 `VALIDATORS`），
前端通过 `/api/composition/check` 调用**同一套逻辑**，不存在两处各写一份的漂移。

### 相关接口

| 接口 | 用途 |
| :--- | :--- |
| `GET /api/composition/schema` | 字段定义与规则（前端渲染的唯一来源） |
| `POST /api/composition/check` | 只校验不求解（前端实时提示） |
| `POST /api/composition/submit` | 先校验，**通过才送求解器**；逐单返回构成与出票结果 |

### 一条容易忽略的约束

**同一人不可能既是残疾人又是孕妇**。早期实现把两个维度的列表按同一个下标
`zip` 到同一位乘客身上，于是生成过"成人1 = 重度残疾 + 孕妇37周+"这种组合。
现在改为顺序填充，两者占据不同位置；总数超过该年龄段基础人数时由
`validate_group_consistency` 报错（见坑点 19）。

## 🧑🤝🧑 批量提交订单：任意张数 × 每张任意人数与类型

**这是验收主入口**（`/booking` 页面下半部分）。
点「提交全部订单」后逐单求解，**不能满足的订单会明确告出原因**。

界面分三块：

1. **左侧乘客类型面板**（18 种，按角色分组）：点一下就加入"当前订单"；
2. **右侧订单清单**：`+ 新建订单` 建任意多张；每张单可加任意多人、可删人、
   可设备注与**绑定强度**（自动 / 硬绑定 / 强绑定 / 软绑定）；
   一键「载入示例（含不可行订单）」可直接看到完整效果；
3. **提交后**：顶部统计 + **需要确认的例外** + 需要现场处理的订单 +
   座位图（按订单着色）+ 逐单结果。

#### 出票是第一原则：特殊席位不够也照常出票，但会**提示/询问**

这是本引擎的运营口径，也是整套实现反复回归到的原则：

> **能出票就出票。** 拒票（候补）只应发生在"全车确实没有空座"这一种情况下。
> 特殊席位（无障碍专区、同车厢相邻）不够时，正确做法是**照常出票 +
> 明确告知旅客与列车员怎么处理**，而不是替旅客拒绝。

#### 结果分五档

| 档位 | 含义 |
| :--- | :--- |
| **全部出票** | 全部出票，且相邻/照护需求都满足，无需处理 |
| **已出票（用户已确认例外）** | 有需要用户拍板的例外，**票已出**，确认后生效 |
| **已出票，需现场处理** | 全部出票，但需站车协助（如专区售罄改发普通座位） |
| **部分出票，其余候补** | 只有"全车余票不足"才会走到这一档 |
| **无座可发（全车已满）** | 全车确实没有空座 |

#### 需要用户确认时会**问出来**（而不是直接拒票）

| 原因码 | 触发条件 | 询问内容 |
| :--- | :--- | :--- |
| `WHEELCHAIR_OVER_QUOTA` | 单张订单轮椅旅客偏多 | 是否仍然出票？超出者坐普通座位，列车员协助上下车 |
| `NO_WHEELCHAIR_SLOT` | 专区余票少于本单轮椅旅客数 | 是否接受『照常出票 + 站车协助』？ |
| `HARD_BOND_INFEASIBLE` | 要求同车厢，但最空的单车厢也装不下 | 是否接受『先出票、上车后找列车员调剂』？ |
| `NO_SEATS` | 全车余票不足（**唯一会候补的情形**） | 无询问，只能候补 |

实测（7 张订单 / 25 人，其中 1 张是"8 位轮椅"）：
**25/25 全部出票、候补 0、无座可发 0、6 张直接全部出票、
1 张触发确认询问并生成站车协助提示、Tier 0 = 0、总耗时 1.7 s**。

> 那 8 位轮椅旅客**全部出了票**：前 7 位进无障碍专区（专区只有 10 座、
> 单张订单建议不超过 2 位），第 8 位坐普通座位 `01车05A`，
> 并生成提示"请站车协助（无障碍踏板 / 就近调剂到专区）"。
> 同时页面向用户**问了一句**："是否仍然出票？"—— 出票优先不等于不告知。

## 🎯 CP-SAT 建模要点（V2.0）

问题被建模为**带约束的二部图匹配**，决策变量 `x[p,s] ∈ {0,1}` 表示"乘客 p 坐座位 s"：

| 类别 | 约束 / 目标 | 实现方式 |
| :--- | :--- | :--- |
| 硬 | 每人至多一座、每座至多一人 | `Σ_s x[p,s] ≤ 1`、`Σ_p x[p,s] ≤ 1`（用 ≤ 而非 =，装不下就候补，避免模型不可行） |
| 硬 | 轮椅旅客只坐无障碍座位 | **候选池内嵌**：建模前就剔除违规座位 |
| 硬 | 硬绑定必须同车厢 | `Σ_{s∈car_c} x[p,s] == Σ_{s∈car_c} x[q,s]` 对每个车厢成立 |
| 硬 | 硬核单元整体就座或整体候补 | `Σ_s x[p,s] == Σ_s x[q,s]`，杜绝"孩子上车、家长候补" |
| 软 | 个体亲和度 | 目标函数一次项（与 V1 同源的打分器） |
| 软 | 座对加成 / 分离惩罚 | 标准线性化：`y ≤ x_a`、`y ≤ x_b`、`y ≥ x_a + x_b − 1` |

**关键设计**：把"跨车厢"这一最重的惩罚**从目标函数里删掉**，改为候选池的结构性约束 —— 强绑定乘客只保留共同车厢的候选。这样既避免了二次项，又让 Tier 0 从"巨额罚分"升级为"不可行"。

## 🕳️ 踩坑记录

这部分保留下来，因为它们恰好说明了"为什么这个项目的每一层都要有硬校验"。**每一条都是被测试或暴力枚举抓出来的真实缺陷。**

### 坑点 1：两人拿到同一个座位号（最严重）

测试夹具把每节车厢的编号都写成了常量 `1`，导致 30 个座位共享 12 个 ID，**两位乘客被静默分配到同一个物理座位**，而所有断言都是绿的。

→ **修复**：编组构造期强制校验座位 ID 全局唯一，分配期再校验一次；`mini_formation` 改为唯一车厢编号。

### 坑点 2：符号反转 —— 求解器把最差的方案当成最优

代价函数里惩罚是负数、奖励是正数，而求解器在做**最小化**。结果是"能拿奖励的方案"被当成"代价最高"而拒绝，**带娃家庭被系统性地排进静音车厢**。

→ **修复**：全链路统一为 affinity 语义（**越大越好**），所有比较改为取最大值；新增断言 `test_exact_solver_beats_or_ties_greedy`。

### 坑点 3：Tier 量级失衡，代价函数失去分辨力

`T1_CONFLICT_ISOLATION`（−10,000）被误用于**所有**带娃家庭，一举压垮其他所有比较；与此同时 Tier 3 的静音车厢奖励按人头累加，**反向利好**错误行为。

→ **修复**：Tier 1 只对"硬冲突群体"（轮椅、独立视障、智力障碍）生效；静音车厢改按**出行单元**计价；新增每人奖励硬上限 60 分。

### 坑点 4：4 个配置项只是"声明了"，从未被读取

`aisle_crossing_weight`、`near_door_rows`、`near_toilet_rows`、`min_floor_reward` 四个参数**调了没用、看起来却生效**。

→ **修复**：把它们真正接进编组与打分器；新增**卫生不变量**测试，静态扫描 `EngineConfig` 的每个字段是否真被代码引用，未引用即失败。

### 坑点 5：自研精确求解器的"代理目标漂移"（V2.0，最值得记的一条）

为了在装不上 `ortools` 的环境里也能精确求解，我手写了匈牙利松弛 + 分支定界，并把代价函数**手抄**进了搜索目标。结果连续三次给出错误答案，**每一次都靠暴力枚举才发现**：

| 轮次 | 返回方案的真实亲和度 | 真实最优 | 根因 |
| :--- | ---: | ---: | :--- |
| 1 | −3470 | +130 | 搜索目标漏掉单元级安全底线 `T1_ISOLATED_CARE_MEMBER` |
| 2 | −2890 | +60 | 漏掉静音车厢团体项 `T3_QUIET_GROUP_OVERUSE` |
| 3 | 105 | +130 | 上界漏掉"未放置 ↔ 已放置"的成对额度，**最优分支被误剪** |
| 4 | 标注 `OPTIMAL` 但结果错 | — | 单元级惩罚在"支持人尚未放置"时就被计入，中间节点被误判为极差 |

**结论**：自研精确求解器若要与权威代价函数**逐节点一致**，必须把整套代价函数增量实现一遍；任何遗漏都会让搜索**系统性地选错**，而且表面上看不出问题 —— 这属于"看起来能跑、实际给错答案"的危险区域。

→ **修复**：不再自研精确目标。`v2_exact` 改为复用 V1 已被底线套件守护的评估实现（按构造成立正确），并在结果 `notes` 中说明来源；匈牙利算法件作为独立可用件保留，由 120 组随机矩阵与暴力枚举交叉验证。V2.0 真正的运筹学路线是 CP-SAT —— 把约束交给成熟求解器，不存在代理目标漂移。

### 坑点 6：学习型策略退化成"把所有乘客都候补掉"（V3.0）

PPO 训练后策略学会了**什么都不做**：候补既不违反任何约束、也不扣分，于是成了最优策略，就座率 0%。同时暴露两个工程缺陷：奖励量级失控（亲和度在 ±10⁴ 量级直接当奖励，价值损失飙到 3×10⁹）、以及**动作掩码没有屏蔽已落座乘客**（导致 episode 只推进 1 步）。

→ **修复**：亲和度按"每位乘客参考量级"归一化；给出**显著高于**亲和度波动的就座正奖励；候补惩罚调整为重于任何座位亲和度差异；掩码屏蔽已落座乘客。修复后就座率从 0% → 62%。

### 坑点 7：推理路径依赖当前工作目录

策略权重用相对路径 `artifacts/v3/v3_ppo.pt` 加载，从别的目录启动服务时**静默退化为随机初始化**，表现是座位图里出现明显不合理的分配。

→ **修复**：所有权重路径基于**工程根目录**解析（`Path(__file__).parents[2]`）。

### 坑点 8：行为克隆把"拒票"当成了正确答案（V3.0）

用 V1 的整单解当老师做行为克隆，第一版跑出来 **78% 的标签是"候补"**，策略于是
学会了把旅客全部候补掉（就座率 19%）。根因很隐蔽：

> V1 在**全部 909 个座位**里搜索，而策略网络只看到 **48 个候选座位**。
> 老师选的座位**根本不在学生的可行动作空间里** —— 投影失败就退化成"候补"。

→ **修复**：把老师的搜索空间**限制在同一个候选池内**（用候选池构造一个受限编组再交给
V1 求解）。修复后池内命中率从 ~0% 升到 ~91%，老师就座率 0.985，候补标签 0%。

**教训**：行为克隆里"老师的动作学生必须做得到"，这比"老师有多强"更关键。

### 坑点 9：逐步贪婪的老师教出了"把一家人撒开"（V3.0）

改用"每步选边际增益最大的座位"当老师后，单步看无懈可击，但一家三口被放成
`01车01A / 01车07D / 01车08A`：第二位家长占了远处的座位，等孩子落座时
**已经没有相邻位置**，于是既有孤立惩罚（−3500）又白占两个座。

诊断方法值得记下来：把**老师和策略放在同一环境里跑**，两者指标几乎相同
（−3420.5/16 vs −3425.5/16），说明问题在**老师的目标**而不是策略的学习能力。
根因是老师的目标只算了"个体项 + 成对项"，漏了单元级孤立项，而且它看不到后续。

→ **修复**：老师改回**整单求解**（V1 分支限界），天然不会犯这种"局部最优导致
全局事故"的错。这正是"行为克隆要用整单最优当老师"的价值。

### 坑点 10：`env.step` 的候补分支不改状态，导致静默死循环（V3.0）

环境的 `step()` 只在"落座"分支把乘客移出 `pending`，**候补分支什么都不改**。
于是当老师连续选择候补时，episode **永不结束也不报错** —— 表现为数据采集脚本
静默卡死（第 300 秒还没打印下一行），极难定位。

→ **修复**：无论落座还是候补都必须把该乘客移出 `pending`。这类"状态不变但循环
继续"的缺陷是所有 agent 环境的共同陷阱，值得单独写一条测试守住。

### 坑点 11：把商务座算成了 51 座（编组容量失真）

**这条是验收时被用户当场看出来的** —— 他问"8 车之后的车厢座位数量怎么不对了"。

原实现让 16 节车厢**共用同一个排数**（默认 17），只靠"减少列数"区分坐席：

| | 旧实现 | 实际 CRH |
| :--- | :--- | :--- |
| 二等座（3+2） | 5 列 × 17 排 = **85 座** | 85-90 座 ✅ |
| 一等座（2+2） | 4 列 × 17 排 = **68 座** | 约 48 座 ❌ |
| 商务座（1+2） | 3 列 × 17 排 = **51 座** | 10-18 座 ❌ |

**为什么这不只是"数字不真实"**：座位数是**容量上限**，直接决定"满座时会不会拒票"
"无障碍专区能服务几位轮椅旅客""压力测试能不能跑满"。一个把商务座容量**夸大 4 倍**
的模型，会让压力测试得出过于乐观的结论 —— 旧基准里"436 单装满"其实就是被虚高的
容量撑起来的。

**修正**：按真实编组给每节车厢独立的排数。

| 车厢 | 坐席 | 布局 | 排数 | 座位数 |
| :--- | :--- | :--- | ---: | ---: |
| 1 车 | 二等座 + 无障碍专区 + 卫生间 | 3+2 | 16 | 80 |
| 2-7 车 | 二等座 | 3+2 | 17 | 85 |
| 8 车 | 二等座 + 卫生间 | 3+2 | 14 | 70 |
| 9-12 车 | 一等座 | 2+2 | 12 | 48 |
| 13 车 | 商务座 + 卫生间 | 1+2 | 4 | 12 |
| 14-16 车 | 商务座 | 1+2 | 5 | 15 |

总容量 **1156 → 909 座**，且座位数按坐席严格递减（商务座 < 一等座 < 二等座）。
新增 `test_real_formation_seat_counts_are_realistic` 把这条守住 —— 它会检查
"各车厢排数不完全相同"以及每类坐席的座位数是否落在现实区间。

修正后重测基准，平峰 P99 从 49.24 ms 降到 **23.73 ms**（容量诚实之后，长尾压力反而更接近真实分布）。

### 坑点 12：硬约束被三条"旁路"绕过（并发压力测试抓出来的）

做并发下单模拟时，一次性压 18 种人群，暴露出**三个独立的绕行路径**，
它们都能让"不可违反"的约束失效：

1. **信用体系在入口被丢弃**：`engine._prepare_order` 用信用账本默认分（100）
   直接覆盖订单申报分（45）。结果是"已投诉屏蔽的旅客照样被排进静音车厢" ——
   因为对引擎而言他根本没有被屏蔽。修正为取两者较低值。
2. **候选池缓存串用**：`SolverTables._unit_cache` 的键只有 `unit.ids`，
   而候选池是按"构造时的可用座位"算的。先构造的实例（座位多）与后构造的实例
   （座位少）**共用同一个键**，于是用了别的座位表算出的候选，硬约束过滤被整体绕过。
   修正为把座位表指纹并入缓存键。
3. **`fallback` 放行 Tier 0**：`_greedy_place_unit` 的最后一道兜底会返回
   "违反 `mandatory_ok`"的放置，注释里甚至写着"硬核单元被拆开时不返回"。
   于是在无障碍专区不足时，"轮椅旅客 + 家属"被拆到 6 车与 7 车。
   修正为宁可整单候补，也不拆散硬绑定。

**共同的教训**：这三处都不是"罚分给小了"，而是**约束根本没被执行**。
本项目的经验是 —— **罚分只能影响"选哪个"，只有候选池与入口校验才能决定"能不能选"**。
现在有 30 + 4 条断言分布在候选池、入口、并发三个层面守着这一点。

### 坑点 13：无障碍专区被**普通旅客**吃光，轮椅旅客反而无座（空车也拒票）

**这条同样是验收时被用户当场问出来的** —— "为什么空车都做不到全部出票？"

顺着这个问题查下去，发现专区 10 个座位里有 **6 个被普通旅客占用**：

| 占用者 | 有没有无障碍需求 | 座位 |
| :--- | :--- | :--- |
| 情侣 / 夫妻 | 无 | 01车01A、01车01B |
| 带娃家庭（家长 + 儿童） | 无 | 01车02A、01车02B、01车02C |
| 独立视障旅客 | 无（只有过道偏好） | 01车01C |
| 智力障碍旅客 + 照护人 | 无 | 01车02D、01车02F |

根因是 `t3_accessible_misuse`（非轮椅旅客占用专区的机会成本）**默认值就是 `0.0`**，
等于完全没有保护 —— 而且代码注释里还写着"默认关闭，可设为负值以启用"，
把一个**必须开启**的安全项写成了可选开关。

用户随后看到的 `60 单 / 145 人 · 出票 137（94.5%）`、`50/50 同车厢` 里那 **8 位候补**，
就是这么来的：专区被占满后，后到的轮椅订单无处可去。

**修正三处**：

1. `t3_accessible_misuse` 默认 **−15.0**，让普通旅客优先选普通座位。
   量级讲究：要**高于**普通旅客能从专区得到的任何好处（专区本身没有奖励，
   只有"近车门"等 +20 级设施奖励），又要**远低于** Tier 1/2 的结构性惩罚
   （−3000 起），以免为了避开专区而拆散家庭；
2. **专区配额**：单个订单最多占用专区的一半（`ZONE_QUOTA_RATIO = 0.5`），
   这样专区至少能服务两个批次，也更贴近"专区要留给随时可能出现的重点旅客"；
3. **混合组合始终可选**："轮椅进专区 + 家属同车厢"不再只在"无处可去时才用"，
   而是作为常备候选交给评估挑选 —— 专区充裕时自然选"全家都在专区"，
   专区紧张时退化为"轮椅进专区、家属同车厢"，而不是整单拒票。

修正后同一场景：**26/26 全员出票、Tier 0 = 0、专区只用掉 4 座**（留给后续轮椅旅客 6 座）。

### 坑点 14：自动组单里连踩四个坑（"看起来配好了、其实没有"）

做"模块化乘客类型"时，**同一个函数改了四轮**才做对。四个坑都属于同一类：
**订单看起来生成了，但照护关系根本没配上** —— 日志、计数、页面全都正常，
只有把订单打出来看"谁和谁在一起"才会发现。

| # | 错误做法 | 症状 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 1 | 按"类型"各自补照护人 | 先处理的轮椅旅客把照护人用光，儿童生成孤身订单 | 先数清全部被照护者，再统一补齐 |
| 2 | 用 `id()` 判断照护人是否已占用 | `replace()` 产生的是新对象，判重失效，自由池恒为空 | 用**稳定序号 + 显式条件**（`group_key is None`）表达占用关系 |
| 3 | 给儿童补照护人，不看已有成人 | 勾"成人 6 + 儿童 2"凭空多出 2 位乘客 | 成人优先充当家长（`ADULTS_ARE_CAREGIVERS`），不够才补人 |
| 4 | 用 `needs_caregiver` 判定"是儿童" | `companion_child` 的该标志为 `False`，被生成孤身订单 | 用 **`role == "child"`** 判定 |

第 4 条的教训最值得记：**用一个"看起来对"的布尔字段当分类判据，很容易漏掉边缘类型**。
现在 `test_modular_archetypes_and_auto_grouping` 会强制检查
"没有被照护者孤身成单"，并把成人当家长的规则也纳入校验。

顺带记一个过程教训：这个函数被我**连续打补丁四次**，每次都只修当前症状，
结果越改越绕（甚至出现同一个乘客被生成两次）。最后**推倒重写**成
"展开人员清单 → 补齐照护人 → 配对 → 折叠成订单"四步，才一次性做对。
**当一个函数被改了四次还在出问题，说明该重写而不是继续打补丁。**

### 坑点 15：一张订单就能把整条出票链路堵死（无时间上限的贪心）

做"手工构造订单"时暴露的**生产级缺陷**：用户提交"一张单 8 人（其中 4 位轮椅）"，
服务端**永远不返回** —— 不是慢，是卡死，HTTP 请求直接超时，整条链路被一单堵住。

追下去发现是**两个独立的组合爆炸**，而且都发生在"看起来有上限保护"的地方：

**① 候选池构造时对整节车厢做组合枚举**

```python
for combo in combinations(slots, size):   # slots = 85 个座位，size = 8
    if self._facility_ok(unit, combo):
        combos.append(combo)
    if len(combos) >= 20:                 # ← 这个"上限"完全无效
        break
```

`C(85, 8) ≈ 3×10¹⁰`。写"凑够 20 个就 break"的人（我）以为这是上限，
但**前 20 个合法组合可能要遍历上亿次**——上限只在"很快凑够"时才起作用。
修正：先按个体分把车厢缩到 `2 × size + 4` 个候选座位，再在小集合上取组合。

**② "轮椅进专区 + 家属同车厢"的笛卡尔积**

```python
for zone_pick in combinations(zone_here, wheelchair_count):
    for other_pick in combinations(others[: need_others + 4], need_others):
```

专区 10 座取 4、其余数百座取 4 —— 约 20 万次评估，每次还要跑 `fs.row()` 查表。
修正：`others` 只取必要数量 + 2 个余量，并加显式枚举上限 `_MIXED_SEARCH_CAP = 400`。

**③ 顺带发现贪心完全没有时间预算**

`assign_exact` 有 `default_exactness_budget`，但 `assign_greedy` **一个时间检查都没有**。
即使组合枚举没爆，候选多时也会慢慢磨。修正：新增
`EngineConfig.greedy_time_budget_ms`（默认 80 ms），整单共享一个截止时刻，
超时返回"当前最好结果"并记录说明——部分出票好过不返回。

**结果**：同一张订单从**永不返回**变成 **81.8 ms 返回**（且直接给出可操作的原因）。

**教训**：`for` 循环里的"凑够 N 个就停"**不是上限**，它只在数据分布配合时才有效。
真正的上限要么缩小输入集合，要么显式计数并在计数上设界。

### 坑点 16：可行性判定说"可满足"，求解器却给出全候补

用户提交"一张单 8 人（4 轮椅 + 4 家属）"，页面显示 **无法满足**，
但原因写的是一串内部编号（`caregiver-2-5 未出票…`）—— 用户看不出该怎么办。

查下去发现**真正的根因在判定逻辑**：`analyse_order` 只检查了
"专区空位数 ≥ 轮椅人数"（10 ≥ 4，通过），**没检查"同一车厢能否装下整单"**。
于是它判"可满足"，求解器却因为车厢装不下而全部候补。

**判成"可满足"再失败，比直接说"不能满足"更糟**：用户拿到的是一串内部 ID，
而不是可操作的建议。

**修正两处**：

1. 补上**同车厢容量检查**（最空的单个车厢余票 vs 整单人数），
   并区分"含轮椅"与"不含轮椅"两种情形给出不同建议；
2. 新增**运营约束** `max_wheelchairs_per_order = 2`：单张订单的轮椅旅客不超过
   专区配额（10 座的一半）。让一单塞 8 位轮椅既会吃光专区（后续轮椅旅客无座），
   又会让组合枚举爆炸。超限时直接告知"请拆成多张订单"。

**顺带修了一处提示排序**：原因列表原先把"N 位旅客未出票：编号列表"排在第一位，
现在**可行性原因排最前** —— 那才是用户能据此行动的信息。

### 坑点 17：把"专区不够"判成拒票，与出票优先直接冲突

用户提出"**还是要以出票为目的，即使特殊席位不够了也可在提示/询问后出票**"，
这才发现我在修组合爆炸时**把安全阀拧过了头**（见坑点 15/16）：

为了让"8 位轮椅挤一张单"不再卡死，我把它判成 `blocking` **直接拒票**。
但这违背了本引擎的第一原则 —— 当时全车还有 **895 个空座**，
却告诉用户"无法满足"。

**修正分成四层**，每一层都是"拒票 → 出票 + 提示/询问"：

| 层 | 改动 |
| :--- | :--- |
| 判定层 | 只有 `NO_SEATS`（全车无空座）才是 `blocking`；其余全部 `advisory` + `question` |
| 求解层 | 专区不够时允许发普通座位（`_carriage_combos` 与 `_enforce_facility_constraints` 都加了这条出口） |
| 候选池层 | 新增 `_compose_fallback_combos`：按人需求直接拼同车厢组合（见下） |
| 界面层 | 新增"需要你确认的例外"区域，把 `question` 显式问出来 |

**候选池层为什么必须有**：`_carriage_combos` 的第一层是"整排连续窗口"，
而二等座**一排只有 5 座** —— 8 人单元**永远**窗口不出来，
于是候选池为空、整单候补，即使全车 895 个空座。这个缺陷只在
"单元人数 > 单排列数"时才暴露，小订单永远测不到。

### 坑点 18：Tier 0 指标被"同一张单内的先后顺序"误伤

修完上面那条后，页面上出现一个自相矛盾的结果：ORD-7 显示"8/8 出票"，
却又标着"部分出票"，且 `Tier 0 = 1`。

追下去发现是**指标分类错误**，不是真的违规：

* `accessible_available` 在**整单开始前**采样一次（当时专区还剩 7 座 → `True`）；
* 同一张单里的 8 位轮椅旅客，前 7 位把这 7 座用掉；
* 第 8 位只能坐普通座位 → 被 `Scorer` 判成"专区还有空位却没给他"，
  记为 **Tier 0 求解器失误**。

但它实际是"**专区不够**"的服务例外，应记 T5 + 站车协助提示。
**Tier 0 是安全底线指标，被这种情况污染会让我们失去对真实事故的警觉。**

**修正**：把专区可用性的判断从"整单开始前算一次"改为
"**每个单元开始前重算**"（`tables._zone_short_for(unit)`），
不足时把 `scorer.accessible_available` 置 False。

修正后 ORD-7：**`tier0 = 0`**、档位 `action_required`（已出票，需现场处理），
提示为"无障碍专区已满，已为 wheelchair-7-8 出票普通座位 01车05A。
请站车协助（无障碍踏板 / 就近调剂到专区）"。

### 坑点 19：残疾与孕妇被 `zip` 到同一个人身上

做"人员构成"时，一位成人同时被标成"重度残疾"和"孕妇 37 周+"。

根因是映射实现把两个维度的列表按**同一个下标**对齐：

```python
level = dis_levels[index] if index < len(dis_levels) else None
stage = preg_stages[index] if index < len(preg_stages) else None
```

残疾名单是 `["severe"]`、孕妇名单是 `["term"]`，两者下标都是 0，
于是**第一位成人同时拿到了两个标签**。这在物理上不可能，用户一眼能看出荒谬，
但计数上完全"自洽"（各维度之和都没超），所以数量校验抓不住它。

**修正**：改成顺序填充 —— 先放残疾人，再放孕妇，各自占据不同位置
（`_expand_attributes`）。总数超过该年龄段基础人数时由
`validate_group_consistency` 报错。

**教训**：两个"互斥属性"的列表绝不能用同一个下标对齐。
只要它们的长度可以不同，就一定会在某些输入下撞车。

### 坑点 20：把"可选登记"当成"必填项"，误拒正常订单

规格里"陪同人数"是一个**可选**的计数器组件（`CompanionCounter`），
而出票资格由"可用健康成人 ≥ 所需成人陪同"决定。

第一版把 `companion_count` 默认成 `0`，并在校验里写"不得少于所需陪同数"。
于是**"成人 1 带 1 个儿童"这种最正常的订单被拒票**：

```
所需成人陪同至少 1 名，当前仅登记 0 名
```

问题在于把"用户没填"当成了"用户填了 0"。

**修正**：`companion_count` 默认 `None`（未登记），只在**确实登记了**的时候
才校验它与可用健康成人的关系。出票资格仍然只看可用健康成人数。

**教训**：可选输入的"未提供"与"提供了零值"是两种不同状态。
用 `0` 当默认值会把后者强加给前者，产生"没填就被判错"的假失败。

### 坑点 21：对整份 HTML 数括号，被中文全角括号骗了

给 OrderEditor 写结构校验时，我直接统计整份 HTML 里的 ASCII 括号：

```
圆括号平衡（1030 vs 1038）   ← 假的
```

差额 8 个来自**正文里的中文全角括号** `（` `）`（U+FF08 / U+FF09）——
它们不是 ASCII 的 `(` `)`，但按"数量相等"这种粗暴判据一混就露馅。

**修正**：新写 `smartrail/web/bracket_check.py`，只扫描 `<script>` 段，
并**剔除字符串、模板串与注释**后再做栈式配对。结果显示 JS 括号完全配对。

**教训**：结构校验要"按语言规则解析"，不能"按字符出现次数比较"。
前者能定位到具体行，后者只能给出一个没法排查的差值。

### 坑点 22：顶层重复声明让整个页面脚本静默失效

**现象**：用户反馈"你做的这个完全用不了，哪个按钮都点不动"。

**根因**：`booking.html` 里两个变量被 `let` 声明了两次：

```js
let presetCatalog = [];   // 第 919 行
let concurrentCar = 1;    // 第 921 行
...
let presetCatalog = [];   // 第 946 行 ← 重复
let concurrentCar = 1;    // 第 948 行 ← 重复
```

同一个脚本作用域里 `let` 重复声明是 **SyntaxError**。浏览器的处理是
**拒绝执行整个 `<script>`** —— 一行都不跑，所以 `boot()` 里的
`$("btnsubmit").onclick = ...` 全部没执行，页面上所有按钮都是死的。

**为什么之前的检查全都没发现**：

| 检查 | 结果 | 为什么漏掉 |
| :--- | :--- | :--- |
| 括号配对 | 通过 | 括号确实配对，只是脚本不执行 |
| 标签配对 | 通过 | 标签确实配对 |
| 关键字符串存在 | 通过 | 字符串都在，包括那两行重复声明 |
| HTTP 接口可用 | 通过 | 后端没问题，坏的是前端脚本 |
| 页面级验收 | 通过 | 抓 HTML 校验字段，**不执行 JS** |

我甚至写了 Node 执行检查，但**第一次跑时垫片自己先崩了**
（`ReferenceError: Cannot access 'document' before initialization`）——
修好垫片后才暴露出真正的 SyntaxError。

**修正**：

1. 删掉重复声明；
2. 新增 `smartrail/web/js_lint.py`：纯 Python 检查**顶层重复声明**
   （只查 `let`/`const`/`class`，`var`/`function` 允许重复；只查深度 0，
   函数内部同名变量合法）。用"加回去能报错、去掉能通过"双向验证过；
3. 新增 `tools/check_page_js.py`：Node 真跑 `boot()`、检查 15 个按钮的绑定、
   **逐个点一遍**并捕获异常；
4. 新增 `tools/verify_served_pages.py`：检查**服务实际下发**的四个页面，
   防"本地修好了、进程还在发旧版"。

**教训**："代码写对了"和"代码会执行"是两件事。
语法错误让整段脚本静默失效，而**所有基于字符串匹配的静态检查对它完全免疫**。
页面级验收如果只抓 HTML 不跑 JS，就只是一张更复杂的字符串检查表。

### 坑点 23：检查脚本自身的两个假阳性

同一轮里，两个新写的检查报了假错：

**（1）`</script>` 包含子串 `<script`**

```python
opened = text.count("<script")   # 把 </script> 也数进去了
closed = text.count("</script>")
# → "<script> 开 2 个 / 闭 1 个"
```

改成正则 `r"<script[\s>]"`（要求开标签后跟空格或 `>`）。
顺带发现**我自己写的说明性注释**里出现了字面量 `<script>`，也被正确计入 ——
于是把那句注释改写掉，而不是给计数器开后门。

**（2）中文全角括号被当成 ASCII 括号**

```python
html.count("(") == html.count(")")   # → 1030 vs 1038，假阳性
```

差额 8 个来自正文里的 `（` `）`（U+FF08 / U+FF09）。
改成只扫 `<script>` 段并剔除字符串、模板串与注释。

**教训**：检查脚本也是代码，也会错。新写的检查必须**双向验证**：
故意制造问题看它报不报，修好再看它过不过。
只验证"通过"的检查等于没有检查。

### 坑点 24：词法扫描器不认识模板串插值，把正常页面判成"括号不配对"

做 12306 版购票页时，新写的检查脚本对两个新页面报出：

```
ticketing.html: L45: 字符串 " 未闭合（该行结束前没有配对引号）
ticketing.html: L45: ( 未闭合
```

但**浏览器与 Node 都能正常解析这两个页面**。也就是说，报错的是我的检查器。

根因：扫描器遇到反引号就"找下一个反引号"，**完全不认识 `${...}` 插值**。
页面里第一个模板串长这样：

```javascript
`<div class="cls" style="border:1px solid ${on ? "var(--blue)" : "var(--line)"}">
```

扫描器把 `${on ? "` 里的引号当成了模板串的结束，于是**这一个模板串被当成
跨了 7 行**，中间所有真实代码都被吞掉；其后每一个字符串的起止位置全错，
最终在文件末尾报出"未闭合"。

量化一下：源码里有 **74 个反引号**（37 个模板串），朴素扫描器只识别出 **1 个**。

**修正**：新写 `smartrail/web/js_lexer.py`，做成真正的小状态机：

* 模板串遇到 `${` 就**递归回到代码态**，用花括号计数找到对应的 `}`；
* 支持任意层嵌套（测试里有三层嵌套模板串的用例）。

**接着又踩到第二个坑**：修好模板串后仍报 L45 未闭合。那一行是：

```javascript
.replace(/"/g, "&quot;")
```

`/"/g` 是**正则字面量**。不识别正则的扫描器把 `/&/g` 的第一个 `/` 当成
注释开头，**整行被当注释吞掉**，于是这一行真实的引号又全错位了。

修正方式是按"前一个有效记号"区分正则与除号：前面是值（标识符/数字/`)`/`]`/`}`）
则是除号，否则是正则开头。这里还有一个细节：**`=` 不是值**，
所以 `const a = /abc/` 里 `a` 后面隔着 `=`，判断依据必须是**紧邻的前一个记号**。

**教训**（本项目第三次吃到同一类亏）：

> 写检查器的时候，**"它能通过"和"它说得对"是两件事**。
> 新写的检查必须**双向验证**：故意制造问题看它报不报，正常代码看它过不过。
> 只验证"通过"的检查，很可能只是一个永远说 OK 的摆设。

### 坑点 25：`str` 是 `Sequence[str]`，一个座位号被当成 5 个座位

做开发者台账时，我用 `mark_occupied("02车01A")` 占座，结果
`occupied` 从 0 变成 **5** —— 字符串被**逐字符**迭代，
占用了 `0`、`2`、`车`、`1`、`A` 这五个"座位"，真正的座位一个都没占上。

这个错误类型检查看不出来、运行时不报错，只会让余票数字莫名其妙地对不上。

**修正**：在 `smartrail/clustering.py` 的 `_as_seat_ids` 里显式拦截：

```python
if isinstance(seat_ids, str):
    raise TypeError("seat_ids 不能是单个字符串（会被逐字符迭代）……")
```

**教训**：凡是接受"ID 序列"的接口，都要显式拒绝单个字符串。
Python 里 `str` 满足 `Sequence[str]`，这个陷阱对类型标注完全隐形。

## 📉 V3.0 训练复盘
### 阶段一：纯 PPO（失败，但排除了错误方向）

```text
PPO 120 轮 / 32 episodes per update / CPU / 312 秒
评估（30 episodes）：就座率 0.684，候补 25 人，Tier 0 = 0，孤立 0，平均亲和度 −603
```

纯 PPO 在"就座率"上明显吃亏：**序列选座的信用分配极难** —— 一位乘客的座位选择
要到整单结束才体现好坏，而策略只能看到稀疏的终局奖励。

### 阶段二：行为克隆（成功，V3 就座率提升到 100%）

```text
采集 1500 单（老师 = V1 整单解，搜索空间限制在候选池内）
老师平均就座率 0.985，池外投影比例 9.1%，样本 3669 条，候补标签 0%
BC 训练 35 epochs / 322 秒 / CPU，最终动作准确率 0.799

同口径 30 episodes 对照：
  PPO（旧）就座率 0.684 / 候补 25 / 亲和度 −603
  BC（新） 就座率 1.000 / 候补  0 / 亲和度 −874
```

**结论**：就座率从 68% → **100%**、拒票从 25 人 → **0 人**、Tier 0 保持 0。
代价是平均亲和度略低（−874 vs −603）：策略学会了"先把人安排下"，
但座位选择的精细度还没追上 V1。

### 阶段三：待做的事（按性价比排序）

1. **PPO 微调**：以 BC 权重为起点继续训练，让策略在"会就座"的基础上优化亲和度
   —— 这是当前最直接的提升点，`train(initial_checkpoint=...)` 已预留接口；
2. **课程学习**：从单人订单开始，逐步增加订单规模与约束密度；
3. **把单元级孤立项纳入老师目标**：当前 BC 策略仍偶有孤立照护（3 例），
   根因是投影噪声与损失函数只按"动作匹配"计分，没有对"孤立"加代价；
4. **改为"价值网络 + 精确解码"**：网络只学价值函数，用 V1 的搜索做解码。

### Tier 0 由硬安全过滤器保证（设计决策）

实测发现：纯学习型策略会把儿童候补掉（它学到的偏好是"少担风险"）。这与本项目的底线设计冲突 —— **Tier 0 是绝对约束，不应依赖模型是否学到**。因此采用分层做法：

- 学习型策略负责**偏好排序**；
- **硬安全过滤器**负责**底线**：需照护乘客的候选被限制在支持人所在车厢（事前），决策后还有一道修复（事后）。

过滤器是确定性的、可审计的。**在报告与验收页中都如实标注这是过滤器的功劳，不把它算作模型的功劳。**

## ⚙️ 配置卫生不变量

一次真实事故：早期版本里有 4 个配置项只是"声明了"，从未被任何代码读取 —— 调参看起来生效、实际毫无作用。现在这类问题由机器守住：

- `test_every_config_field_is_actually_used` 静态扫描 `EngineConfig` 的**每个字段**是否真被 `smartrail/` 下的代码引用，未引用即失败；
- `test_config_wiring_affects_behaviour` 用行为验证：调整 `near_door_rows` 会改变近车门座位数量、调整 `aisle_crossing_weight` 会改变跨过道距离、抬高 `min_floor_reward` 会停止发放碎片化奖励。
