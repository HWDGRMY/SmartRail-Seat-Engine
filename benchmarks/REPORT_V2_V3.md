## 1. V2.0：运筹学求解

### 1.1 交付物

* `smartrail/v2/registry.py` —— 求解器插件层：协议 + 注册表 + 依赖可用性探测
  （`BackendUnavailable` 显式报错，绝不静默换引擎）
* `smartrail/v2/cpsat.py` —— CP-SAT 建模（**核心交付**）
* `smartrail/v2/exact.py` —— 零依赖后端 + 匈牙利算法件
* `smartrail/v2/heuristic.py` —— V1 后端适配（作为质量基线）

### 1.2 CP-SAT 建模要点

问题被建模为**带约束的二部图匹配**，决策变量 `x[p,s] ∈ {0,1}`：

| 类别 | 约束/目标 | 实现 |
| :--- | :--- | :--- |
| 硬 | 每人至多一座、每座至多一人 | `Σ_s x[p,s] ≤ 1`、`Σ_p x[p,s] ≤ 1`（用 ≤ 而非 =，装不下就候补，避免模型不可行） |
| 硬 | 轮椅只坐无障碍专区 | **候选池内嵌**：建模前就把违规座位剔除 |
| 硬 | 强绑定必须同车厢 | `Σ_{s∈car_c} x[p,s] == Σ_{s∈car_c} x[q,s]` 对每个车厢成立 |
| 硬 | 硬核单元整体就座或整体候补 | `Σ_s x[p,s] == Σ_s x[q,s]`，杜绝"孩子上车、家长候补" |
| 软 | 个体亲和度 | 目标函数一次项（与 V1 同源的打分器） |
| 软 | 座对加成 / 分离惩罚 | 标准线性化 `y ≤ x_a`、`y ≤ x_b`、`y ≥ x_a + x_b − 1` |

**关键设计**：把"跨车厢"这一最重的惩罚**从目标函数里删掉**，改为候选池的结构性
约束 —— 强绑定乘客只保留共同车厢的候选。这样既避免了二次项，又让 Tier 0 从
"巨额罚分"升级为"不可行"，语义更强。

### 1.3 自研精确求解的尝试与结论（重要教训）

在装不上 ortools 的环境里，我尝试自研精确求解器（匈牙利松弛 + 分支定界），
并用**暴力枚举**做交叉验证。结果记录如下，因为它比"成功"更有价值：

| 轮次 | 现象 | 根因 |
| :--- | :--- | :--- |
| 1 | 返回 -3470 分方案（最优 +130） | 搜索目标漏掉单元级安全底线 `T1_ISOLATED_CARE_MEMBER` |
| 2 | 返回 -2890 分方案 | 漏掉静音车厢团体项 `T3_QUIET_GROUP_OVERUSE` |
| 3 | 返回 105 分方案（最优 130） | 上界漏掉"未放置↔已放置"的成对额度，最优分支被误剪 |
| 4 | 状态标注 `OPTIMAL` 但结果不对 | 单元级惩罚在"支持人尚未放置"时就被计入，中间节点被误判为极差 |

**结论**：自研精确求解器若要与权威代价函数**逐节点一致**，必须把整套代价函数
增量实现一遍；任何遗漏都会让搜索**系统性地选错**，而且表面上看不出问题。
这属于"看起来能跑、实际给错答案"的危险区域。

**最终形态**：`v2_exact` 改为复用 V1 已被 28 条断言守护的分支限界（按构造成立
正确），并在 `notes` 中说明来源；V2.0 真正的运筹学路线是 CP-SAT
（把约束交给成熟求解器，不存在代理目标漂移）。匈牙利算法件作为独立可用件保留，
由 40+ 组随机矩阵（含 big-M 稀疏与矩形）与暴力枚举交叉验证。

## 2. V3.0：仿真器 + 图神经网络 + 强化学习

### 2.1 交付物

| 模块 | 内容 |
| :--- | :--- |
| `v3/simulator.py` | 仿真器：订单流生成（9 类客流画像）、列车状态、逐单记账、信用投诉回灌 |
| `v3/features.py` | 二分图特征工程（乘客 22 维 / 座位 12 维 / 候选边 5 维 / 全局 12 维），纯 numpy |
| `v3/gnn.py` | 二分图编码器：座位→乘客、乘客→座位两轮消息传递 + 边打分头（13.7 万参数） |
| `v3/rl.py` | 自研 PPO（GAE、裁剪代理目标、熵奖励、价值裁剪）+ 序列决策环境 |
| `v3/policy.py` | 策略接入统一求解器接口 + **Tier 0 硬安全过滤器** |
| `v3/evaluate.py` | V1/V2/V3 同流对比（同一 seed / 同一指标口径） |
| `v3/train.py` | 训练与评估 CLI，产物写入 `artifacts/v3/` |

**把选座变成序列决策的关键性质**：本问题的亲和度是**可加的**（个体项 + 成对项），
因此"增量亲和度"可以直接作为即时奖励 —— 这是能让 PPO 干净地工作在这类组合优化
问题上的前提。

### 2.2 真实训练结果（PPO，120 轮，CPU，312 秒）

```
最终评估（20 episodes）：平均亲和度 -440.0，Tier 0 = 0，孤立 = 0，
                        就座 31 人 / 候补 19 人，就座率 62%
```

训练过程中修复的三个真实缺陷：

1. **奖励量级失控**（loss ≈ 3×10⁹）：亲和度在 ±10⁴ 量级直接当奖励，价值损失爆炸。
2. **退化为"全部候补"**（就座率 0%）：候补惩罚太轻时，"不做事"是最优策略。
3. **GPU 设备不匹配**与**掩码未屏蔽已落座乘客**（episode 只推进 1 步）。

**诚实结论**：V3.0 的流水线已经打通并能产出真实学习曲线，但当前策略
**尚未超过 V1** —— 就座率 62% vs V1 的 100%，亲和度仍为负值。原因是
"序列选座"的信用分配极难：一位乘客的座位选择要到整单结束才体现好坏。
后续改进方向（按性价比排序）：

1. **行为克隆预热**：先用 V1 的最优解做监督预训练，再 PPO 微调（最直接）；
2. **课程学习**：从单人订单开始，逐步增加订单规模；
3. **改为"价值网络 + 精确解码"**：网络只学价值函数，用 V1 的搜索做解码。

### 2.3 Tier 0 由硬安全过滤器保证（设计决策）

实测发现：纯学习型策略会把儿童候补掉（它学到的偏好是"少担风险"）。
这与本项目的底线设计冲突 —— **Tier 0 是绝对约束，不应依赖模型是否学到**。
因此采用分层做法：

* 学习型策略负责**偏好排序**；
* 硬安全过滤器负责**底线**：需照护乘客的候选被限制在支持人所在车厢
  （事前），决策后还有一道修复（事后）。

过滤器是确定性的、可审计的，且在页面与报告中如实标注 —— 不把过滤器的功劳
算作模型的功劳。

## 3. 验收页面

**路径**：`smartrail/web/acceptance.html`（也可通过 `GET /acceptance` 访问）

| 区块 | 内容 |
| :--- | :--- |
| 数据来源横幅 | 明确区分「后端实时」与「内嵌快照」，并标注快照生成时间 |
| 运行参数 | 订单数 / 随机种子 / 初始占座比例，点「跑对比」调用 `POST /api/compare` |
| 三版本对比表 | 就座率、亲和度、相对 V1 增益、Tier 0、孤立、静音误用、P50/P99；榜单第一高亮 |
| 场景座位图 | 带娃家庭场景下三版本的座位着色（V1 绿 / V2 黄 / V3 紫），可切换车厢 |
| 学习曲线 | 真实 PPO 曲线（平均回报 + 平均亲和度双线），附最终评估 JSON |
| 说明区 | 对比口径、依赖缺失如何呈现、V3 权重来源 |

**离线可用性**：页面把真实快照内嵌进 HTML（138KB），双击即可打开；
检测到后端时自动切换为实时数据。缺依赖的后端（`v2_cpsat` 缺 ortools、
`v3_rl` 缺 torch）会在表格里显示「已跳过 + 安装命令」，不会静默换引擎。

## 4. 复现命令

```bash
# 测试（52 条断言）
python tests/test_safety_guarantees.py     # 28
python tests/test_api.py                   # 5
python tests/test_v2_v3.py                 # 15（缺依赖的检查自动跳过）
python tests/test_frontend_contract.py     # 4
python tests/pytest_shim.py -q             # 离线运行器：52 passed

# V2 自研精确求解的算法件交叉验证（匈牙利 vs 暴力枚举）
python -m pytest tests/test_v2_v3.py -k bruteforce

# V3 训练（需要 torch + numpy）
python -m smartrail.v3.train --updates 120 --episodes 32 --seed 11 --out artifacts/v3
python -m smartrail.v3.train --eval-only --checkpoint artifacts/v3/v3_ppo.pt

# 三版本同流对比（不需要 torch 也能跑 V1/V2）
python -m smartrail.v3.train --compare --steps 60

# 生成并注入验收页面快照
python -m smartrail.report --steps 40 --seed 7 --inject

# 启动验收台
python -m smartrail.api.stdlib_server     # 零依赖，http://127.0.0.1:8000/acceptance
python -m smartrail.api.app               # FastAPI 版（需先 pip install fastapi uvicorn）
```
